# Decisions

The choices behind Kursi, one entry each: the situation, what was decided, and what it costs. Newest decisions are at the end.

## 1. PostgreSQL, not MongoDB

**Context.** The core of the app is one invariant across rows: an event's bookings never outnumber its seats. Users, events and bookings point at each other, and every write that matters touches more than one of them.

**Decision.** PostgreSQL 18. Transactions, row locks, CHECK constraints, partial unique indexes and foreign keys are the tools this problem needs, and Postgres has all of them built in.

**Consequences.** The schema is fixed, so every change is a migration (generated by drizzle-kit, committed as SQL). Nothing here needs documents of varying shape, so that costs little. Scaling past one database server would mean read replicas or partitioning rather than built-in sharding, which is far beyond what an event-booking API needs.

## 2. Drizzle, with the SQL in plain sight

**Context.** The booking logic is a handful of precise SQL statements: a conditional UPDATE, a `SELECT … FOR UPDATE`, a partial unique index. An ORM that hides SQL behind its own model would hide the part of the code that most needs reviewing.

**Decision.** Drizzle ORM. Queries are written in TypeScript but read almost like the SQL they produce, their result types come from the schema, and migrations are plain SQL files in `migrations/`.

**Consequences.** Drizzle is still before 1.0, so an upgrade can break things; Dependabot's weekly PRs and the test suite catch that. drizzle-kit, a dev-only tool, bundles an old esbuild with known advisories that never reach the production image.

## 3. Booking a seat is one conditional UPDATE

**Context.** The first version read the event, checked `seatsBooked < capacity` in TypeScript, inserted the booking and wrote the count back. Against 50 simultaneous requests for 10 seats, it booked all 50 and left the counter at 1: every request read the same count before any of them wrote. ([PR #7](https://github.com/bakirsobashy/kursi/pull/7) keeps that failing commit in its history.)

**Decision.** Take the seat with one statement, in the transaction that inserts the booking:

```sql
UPDATE events SET seats_booked = seats_booked + 1
WHERE id = $1 AND status = 'published' AND starts_at > now() AND seats_booked < capacity
RETURNING *
```

The UPDATE locks the row. A second request for the same event waits for the first to commit, then re-checks the WHERE clause against the new count. Zero rows updated means no seat, and nothing was written.

The alternatives were correct too, but cost more:

- `SELECT … FOR UPDATE`, then check in TypeScript, then UPDATE: right, but the row stays locked across more round trips, so requests for a popular event queue for longer.
- SERIALIZABLE isolation: Postgres detects the conflict and aborts one transaction, so every caller needs retry logic, and under load most attempts are retries.

**Consequences.** When the UPDATE matches nothing, it doesn't say why, so a second query works out whether the event is sold out, cancelled, started or already booked by this person (see entry 5 for where that query runs). The concurrency test sells exactly 10 of 10 seats on every one of its 20 runs.

## 4. A seat counter, not counting booking rows

**Context.** "Is there a free seat?" could be answered by counting confirmed bookings on every request. But a COUNT locks nothing: two requests can both count 9 of 10 and both insert, unless something serializes them.

**Decision.** `events.seats_booked`, a counter on the event row. Booking increments it and cancelling decrements it, in the same transaction as the booking row. That gives every booking for an event one row to lock, and a CHECK constraint, `seats_booked BETWEEN 0 AND capacity`, that the database enforces whatever the code does.

**Consequences.** The counter is a copy of something the bookings table also knows, so it could drift if a write changed one and not the other. Every write changes both in one transaction, and the race tests check after every run that the counter equals the confirmed bookings. `seatsLeft` in responses costs nothing to compute.

## 5. One lock order, and no pool queries inside a transaction

**Context.** Booking, cancelling a booking and cancelling an event all lock an event and bookings. Two transactions that take the same locks in opposite orders can each wait for the other forever. Separately, an early version of the booking code ran its "why wasn't it bookable?" query on the shared pool from inside the booking transaction. Under load, every connection in the pool was held by a transaction waiting for a free connection, and the whole app stalled.

**Decision.** Every write locks the event row first, then booking rows. Inside `db.transaction(...)`, code queries through the transaction only, never through the pool; the explanation query runs after the transaction has ended.

**Consequences.** It's a rule to keep in mind rather than one the compiler enforces. Tests that hold a row lock from a second connection prove the order: while the event is locked, a cancel waits without having locked its booking.

## 6. Rotating refresh tokens with reuse detection

**Context.** Access tokens are JWTs that live 15 minutes, so a stolen one stops working soon. Logging in every 15 minutes isn't acceptable, so a longer-lived refresh token keeps the session going, and that token is the one worth stealing.

**Decision.** The refresh token is 256 random bits in a cookie that is HttpOnly (page scripts can't read it), SameSite=Strict (other sites can't send it), Secure in production, and sent to `/api/v1/auth` only. Each login starts a token family. Each refresh revokes the token it was given and issues the next one in the family, so a token works once. A revoked token coming back while its family is still alive means someone kept a copy, so the whole family is revoked and both the thief and the real user must log in again. The token row is locked during the swap, so two refreshes with one token can't both succeed.

**Consequences.**

- Two browser tabs refreshing with the same token at the same moment look exactly like a replay, so the session ends. A few seconds' grace for a just-rotated token would fix it, at a small cost in security. It's listed in the README under "What I'd do next".
- The session lasts until 7 days without activity; there is no absolute limit.
- Logging out ends the session, but access tokens already issued keep working until they expire, at most 15 minutes.
- Old token rows are never cleaned up; a scheduled job would delete expired ones.

## 7. Argon2id for passwords, SHA-256 for refresh tokens

**Context.** Both are secrets stored only as hashes, so a stolen database doesn't hand them out. But a password is chosen by a person and can be guessed, and a refresh token is 256 random bits and can't.

**Decision.** Passwords use Argon2id, the hash OWASP recommends first: slow and memory-hungry on purpose, so each guess against a stolen hash is expensive. Logging in with an unknown email still checks the password against a dummy hash, so a response's timing doesn't reveal whether an account exists. Refresh tokens use SHA-256. Guessing isn't possible, so slowness would buy nothing, and a fast, deterministic hash means a token can be found by its hash through a unique index.

**Consequences.** Every login and registration spends about 0.1 seconds of CPU on Argon2, which is one reason login is rate limited. argon2 is a native module, which shapes the Docker image (entry 13).

## 8. Errors are Problem Details, from one catalog

**Context.** Clients need to tell "sold out" from "already booked" without parsing English, and the API needs every error of one kind to look the same.

**Decision.** Every error is an RFC 9457 Problem Details object, sent as `application/problem+json`. Its `type` links to the matching heading in [problems.md](problems.md). One catalog in `src/lib/errors.ts` gives each problem type its status and title, so code throws `new AppError('event-sold-out', { detail })` and can't invent a new status or wording. The API docs list, per route, the problem types it can return.

**Consequences.** A new kind of error means a catalog entry and a heading in problems.md, and tests fail until both exist and match. Clients can switch on `type`.

## 9. 404, not 403, for other people's drafts and bookings

**Context.** A draft event is private until it's published. Answering someone else's draft with 403 Forbidden would confirm that it exists.

**Decision.** A draft answers 404 to everyone but its organizer and admins, exactly like an event that doesn't exist. Someone else's booking answers 404 the same way. For published events, whose existence is public, managing someone else's event answers 403, which says more.

**Consequences.** A 404 can't tell a user "this exists but isn't yours", which is the point. Tests check that a stranger can't distinguish a draft from a missing event.

## 10. Registration says when an email is taken

**Context.** Login never reveals whether an account exists: every failure gets the same 401, with the same timing. Registration could keep the same secret, but only by always answering "check your email" and sending a message, which needs an email service this project doesn't have.

**Decision.** Registering an email that's already used answers 409 `email-taken`.

**Consequences.** Anyone can find out whether an email has an account, which is the usual trade-off on sites without email verification. Registration is limited to 5 attempts a minute per IP, which makes checking a long list of emails slow.

## 11. Rules the database enforces, and one place that translates them

**Context.** Application code can have bugs, and two requests can race past a check that looked safe. The rules that must never break should hold even then.

**Decision.** The database enforces them:

- seats between 0 and the capacity;
- end times after start times;
- one confirmed booking per person and event (a partial unique index);
- lowercase emails;
- `cancelled_at` set exactly when a booking is cancelled;
- foreign keys between all four tables.

Services translate the violations they expect into specific answers, such as `already-booked`. Anything else reaches one function, `databaseProblem()`:

| Postgres error                    | Answer                 |
| --------------------------------- | ---------------------- |
| Unique or CHECK violation         | 409 `conflict`         |
| Missing reference                 | 404 `not-found`        |
| Row still referenced              | 409 `conflict`         |
| Statement timeout                 | 503 `database-timeout` |
| Deadlock or serialization failure | 503 `database-busy`    |

Every connection has a 5-second statement timeout and a 10-second limit on idle transactions.

**Consequences.** A bug produces a 409, not corrupted data or a 500. Adding a rule means a migration, not just code.

## 12. API docs generated from the validation schemas, and checked by every test

**Context.** Hand-written API docs drift from the code within weeks, and nothing notices until a client breaks.

**Decision.** The OpenAPI 3.1 document is generated by zod-openapi from the Zod schemas that validate requests. Response shapes are Zod schemas too, and the services use them as their return types. Every response in the test suite is checked against the document: its status must be listed, and its body, error type and headers must match. Swagger UI at `/docs` is pre-filled with the seeded demo data and authorizes itself after a login. It's served from `swagger-ui-dist` with no inline scripts, so the app's strict Content-Security-Policy didn't need loosening.

**Consequences.** Changing a route without changing its docs fails the tests, on purpose. The docs page needs the `public/` folder in the image.

## 13. A Debian-slim image, run as a numbered non-root user

**Context.** The demo has to start with one command on any machine, including Apple Silicon Macs, and the same image should be safe to deploy.

**Decision.**

- **Base image:** `node:26-slim`, Debian-based. argon2's prebuilt binaries target glibc, which Alpine's musl doesn't provide.
- **Stages:** a multi-stage build, so the runtime image holds only the compiled JavaScript, production dependencies, migrations and the docs page.
- **User:** it runs as `USER 1000:1000`, the image's `node` user by number. Kubernetes' `runAsNonRoot` can only verify a numeric user, and refuses a named one.
- **Process:** `node` runs as PID 1, not `npm start`, so Docker's SIGTERM reaches the graceful shutdown.
- **Compose:** runs the same image twice: once to migrate (and seed, when `SEED_DEMO_DATA=true`), then as the API.
- **Build context:** `.dockerignore` is an allowlist, so a secret added later can't slip into the build.

**Consequences.** The image is larger than an Alpine one would be. CI builds it on amd64 and arm64 and checks that argon2 works on both. Demo data is added only when asked, because the demo accounts' password is public.

## 14. Rate limits in memory, keyed on the client IP

**Context.** Login is a password-guessing target, and every endpoint can be flooded.

**Decision.** express-rate-limit, per IP and per minute:

- login: 5 failed attempts (a correct password never counts against you);
- registration: 5;
- refresh: 30;
- everything under `/api/v1`: 300.

Health checks and the docs are unlimited. Behind a proxy, `TRUST_PROXY` must match the setup, or every client shares the proxy's IP. [deployment.md](deployment.md) explains the settings.

**Consequences.** The counters live in the process, so several API instances would each count separately; a shared store such as Redis would fix that. A per-IP limit can't stop an attacker who spreads guesses over many IPs. A lockout per account would, at the cost of letting anyone lock someone else out.

## 15. Tests run against a real PostgreSQL

**Context.** The bugs that matter most here are races, constraint violations and lock order, and mocks can't reproduce any of them.

**Decision.** Every test talks to PostgreSQL 18: a throwaway Testcontainers instance, or `TEST_DATABASE_URL`. Race tests send many requests before awaiting any. Lock tests hold a row lock from a second connection and poll `pg_stat_activity` until the request under test is waiting, so they prove an ordering instead of hoping for one. Each protection was checked by breaking it and watching the right test fail.

**Consequences.** Running the tests needs Docker, or a local Postgres. Test files run one at a time, since they share the database. The suite still runs in under a minute.

## 16. TypeScript stays on 6.0 for now

**Context.** npm's latest TypeScript is 7, but typescript-eslint supports only versions below 6.1.

**Decision.** `typescript@~6.0` in package.json, and Dependabot ignores TypeScript's minor and major updates.

**Consequences.** The project misses TypeScript 7's speed-ups until typescript-eslint catches up. Then the pin and the Dependabot rule both go.
